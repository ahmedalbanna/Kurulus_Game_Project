## 2. Proposed ECS Architecture

### 2.1 Component Changes (kurulus-core)

#### A. Expand `TerrainType` Enum

```
Current:  OpenField | Forest | Water | Mountain | Road | Building
Proposed: OpenField | DenseForest | MediumForest | TallGrass | NightDarkness
          | Ruins | Caves | CropField | ArtificialCover | Water | Mountain | Road | Building
```

**Rationale**: The GDD distinguishes 8 stealth zone types with different detection ranges and capacities. A single `Forest` variant cannot express Dense (5m) vs Medium (8m) detection differences.

**Alternative (less invasive)**: Keep `TerrainType` as-is, add a new `StealthZoneType` enum and a `StealthZone` component on terrain tiles:

```rust
#[derive(Component, Reflect, Clone, Debug, Serialize, Deserialize)]
pub struct StealthZone {
    pub zone_type: StealthZoneType,
    pub capacity: u32,
    pub current_occupancy: u32,
    pub detection_range_static: f32,   // 5m for dense forest
    pub detection_range_moving: f32,   // 8m for dense forest
    pub destructible: bool,
}

pub enum StealthZoneType {
    DenseForest,
    MediumForest,
    TallGrass,
    NightDarkness,
    Ruins,
    Caves,
    CropField,
    ArtificialCover,
}
```

**Recommended**: The alternative approach — keeps `TerrainType` clean for movement/pathfinding while adding a parallel stealth zone layer. This avoids a massive refactor of all terrain-consuming systems.

#### B. New Component: `VisionCone`

```rust
#[derive(Component, Reflect, Clone, Debug, Serialize, Deserialize)]
pub struct VisionCone {
    pub front_angle: f32,      // degrees, default 120°
    pub side_angle: f32,       // degrees, default 180° (peripheral)
    pub front_mult: f32,       // 1.0
    pub peripheral_mult: f32,  // 0.7
    pub side_mult: f32,        // 0.4
    pub rear_mult: f32,        // 0.0 (blind behind)
    pub facing: Vec2,          // direction the unit faces
}
```

**Purpose**: Replaces simple radius checks with angular detection multipliers. The `stealth_detection_system` will compute the angle between detector→target and the detector's `facing`, then apply the appropriate multiplier.

**Lifetime/Sync Risk**: `facing` must be read from `Formation.facing` or `Unit` direction. No mutability conflicts — `VisionCone.facing` is updated by a separate system in `FormationMovement` set, before `StealthDetection`.

## 5. Cross-Cutting Concerns

### 5.1 Lifetime & Sync Risks

| Risk | Mitigation |
|------|-----------|
| `VisionCone.facing` mutated by FormationMovement, read by StealthDetection | Ensure `FormationMovement` set runs before `VisionCalculation` (already ordered) |
| `ObserverState.alert_level` mutated by detection_chain, read by stealth_detection | Both in same `StealthDetection` set — use ordering `.chain()` |
| `AmbushState` mutated by multiple systems (phase, trigger, staged) | Centralize mutations in `ambush_phase_system`, other systems only read |
| `DetectionChain` concurrent mutation from multiple detectors | Use `&mut` query with `for` loop — Bevy guarantees exclusive access per entity |
| `StealthZone.current_occupancy` updated by zone_capacity, read by ambush_auto_hide | Same set, sequential — safe |

### 5.2 Performance Considerations

| Concern | Approach |
|---------|----------|
| Vision cone angle computation per detector-target pair | O(detectors × stealth_units) — acceptable for <1000 units. Use spatial hashing if needed later |
| Detection chain timers | Only active for units with `DetectionChain` component (sparse) |
| Zone capacity tracking | Increment/decrement on entry/exit events, not per-frame recalculation |

### 5.3 Config-Driven Design

All GDD magic numbers (detection ranges, damage multipliers, durations, costs) will live in `AmbushConfig` loaded from `kurulus-config/assets/ambush_config.ron`. This enables:
- Balance tuning without code changes
- Mission-specific overrides
- Easy A/B testing

### 5.4 BRP/MCP Integration

All new components and events will be registered for BRP reflection in `register_logic_plugins()`:
```rust
app.register_type::<VisionCone>()
   .register_type::<ObserverState>()
   .register_type::<DetectionChain>()
   .register_type::<AmbushState>()
   .register_type::<LureTarget>()
   .register_type::<StealthZone>();
```

## 8. Open Questions for the User

Before proceeding to implementation, I'd like to clarify a few design decisions:

1. **TerrainType expansion vs parallel StealthZone layer**: The GDD needs 8 stealth zone types but the current `TerrainType` only has 6 variants. Do you prefer expanding `TerrainType` directly (simpler but touches many systems) or adding a parallel `StealthZone` component on tiles (more modular, less invasive)?

2. **Hit & Run scope**: The GDD has a full hit-and-run system (6-phase cycle, fatigue, withdrawal rules). This is marked as stretch in Phase 4. Should it be included in this sprint or deferred?

3. **Bait Rider as new UnitArchetype**: The GDD defines a Bait Rider unit with unique stats (6 m/s, 100 HP, doesn't stop under fire). Should this be a new `UnitArchetype::BaitRider` variant, or a special entity with custom components?

4. **Config RON location**: Should the ambush config live in `kurulus-config/assets/ambush_config.ron` (loaded at runtime) or be hardcoded initially with config as a follow-up?

5. **Priority**: Given the gap analysis, should I prioritize the **detection overhaul** (vision cones + observer factors) or the **ambush lifecycle** (phases + staged triggers) first? The detection system is more foundational but the ambush lifecycle is more visible to players.
