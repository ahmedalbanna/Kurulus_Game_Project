## 🔴 1. Pathfinding في Bevy ECS — ✅ مكتمل (مبني خصيصاً)

### المشكلة في المشروع (كانت)

- لا يوجد أي pathfinding في الكود
- GDD يحدد 100+ وحدة في المعركة
- `SimulationSet::Pathfinding` موجود كـ system set لكن بلا أنظمة

### ✅ ما تم بناؤه

#### A* مع تكاليف التضاريس (`kurulus-systems/src/unit_command/pathfinding.rs`)

- **CostProvider Trait**: generic interface لكل من `HashSet<IVec2>` (عقبات بسيطة) و`PathfindingGrid` (تكاليف تضاريس كاملة)
- **8-directional octile distance**: diagonal = √2، cardinal = 1.0
- **تكاليف التضاريس**:
  | التضاريس | التكلفة |
  |---|---|
  | OpenField | 1.0 |
  | Road | 0.8 |
  | Forest | 1.5 |
  | Water | 3.0 |
  | Mountain | 2.5 |
  | Building (obstacle) | ∞ |
- **Two‑way pathfinding**: forward + reverse search لكل مسار
- **Dynamic recalculation**: عند تغير العقبات أو انسداد المسار
- **متكامل مع** `UnitCommandPlugin` في `SimulationSet::Pathfinding`

#### Flow Field (`kurulus-core/src/resources/flow_field.rs`, `kurulus-systems/src/flow_field/mod.rs`)

- **Dijkstra wavefront**: BFS queue (بعد إصلاح مشكلة DFS stack) لكل مجموعة وحدات
- **Group detection**: ≥3 وحدات إلى نفس الهدف → Flow Field (توفير هائل مقارنة بـ A* لكل وحدة)
- **عتبة المجموعة**: `GROUP_SIZE_THRESHOLD = 3` (قابل للتعديل)
- **تخزين مؤقت**: `FlowFieldCache` يعيد استخدام الحقول لنفس الوجهة
- **تنظيف تلقائي**: عند وصول الوحدة إلى الهدف
- **حركة O(1)**: لكل وحدة في كل tick

#### PathfindingGrid (`kurulus-core/src/resources/pathfinding.rs`)

- **تكامل TerrainGrid**: يبني `PathfindingGrid` من التضاريس + العقبات في `O(n)`
- **Cost lookup في O(1)**: `grid.cell(x, y)` للوصول المباشر
- **BRP registered**: للتصحيح عبر MCP

## 🔴 2. AI Behavior Trees في Bevy

### المشكلة في المشروع

- `BehaviorTree` component موجود في `kurulus-core/src/components/ai.rs`
- `AIController` مع strategy/goals
- لكن لا يوجد BT evaluation engine — الكود الحالي يكتب أوامر مباشرة عبر events

### ✅ ما تم بناؤه (الأسبوع 2)

#### BT → Utility Bridge System (`kurulus-systems/src/ai/combat_ai_integration.rs`)

- **`bridge_bt_to_utility_system`**: يقرأ `BehaviorTree` و `AIController` من كيانات AI، وينسخ الـ goal والـ strategy إلى `AIBridgeState` كـ HashMap للوصول السريع
- **`resolve_ai_decision_system`**: يقرأ `UtilityThinker` (action الحالي من utility AI) و يقرر ما إذا كان مسموحاً بتنفيذ الإجراء بناءً على `AIPriority`:
  - `AIPriority::UtilityTactical` → السماح دائماً (Utility يتحكم تكتيكياً)
  - `AIPriority::BTStrategic` → السماح فقط إذا كان الإجراء يتوافق مع الهدف الاستراتيجي من BT
- **`action_matches_goal`**: دالة تطابق تلقائياً إجراءات Utility مع أهداف BT (هجوم ← هجوم، اقتصاد ← اقتصاد، دفاع ← دفاع، إلخ)
- **تجاوز الطوارئ**: إذا كانت الصحة < 30%، يتم تجاوز BT والسماح بإجراءات النجاة حتى في وضع `BTStrategic`
- **علامة `IntegrationActionExecuted`**: تمنع التنفيذ المزدوج لنفس الإجراء في نفس الإطار

#### المكونات الجديدة:

| المكوّن | الوصف |
|---------|-------|
| `AIBridgeState` | Resource: خرائط goal/strategy لكل كيان (من BT → Utility) |
| `AIIntegrationConfig` | Component: يتحكم في أولوية التكامل (UtilityTactical / BTStrategic) |
| `IntegrationActionExecuted` | Component: علامة مؤقتة تمنع التنفيذ المزدوج |

## 🔴 3. Stealth/Line-of-Sight في Bevy

### المشكلة في المشروع

- لا يوجد raycasting أو vision check أو fog of war

### الحلول المكتشفة

#### للـ Line-of-Sight:

**Bresenham's Line Algorithm** — الأبسط والأسرع للـ grid-based:

```
fn has_line_of_sight(from: GridPos, to: GridPos, terrain: &TerrainGrid) -> bool {
    // Bresenham's line algorithm
    // يتحقق من كل cell على الخط بين from و to
    // يُرجع false إذا لقي blocked cell
}
```

#### للـ Fog of War: `bevy_fog_of_war` ⭐

- **المطور**: foxzool
- **الفكرة**: GPU-based fog باستخدام compute shaders
- **المميزات**:
    - `VisionSource` component (circle, square, cone shapes)
    - Chunk-based map processing — مناسب للخريطة الكبيرة
    - Explored area tracking
    - Snapshot system (للـ save/load)
    - `Capturable` entities — تظهر فقط عندما يمر بها vision
- **التكامل مع Kurulus**:
    - كل وحدة لها `VisionSource::cone(vision_range, facing_angle)`
    - `Capturable` على وحدات العدو
    - `FogMapSettings.chunk_size` يتناسب مع `CELL_SIZE = 1.0`

#### للـ Detection System:

```
// detection_system.ts pattern
fn stealth_detection_system(
    mut stealth_query: Query<(Entity, &WorldPosition, &mut Stealth)>,
    detectors: Query<(&WorldPosition, &Detection)>,
    terrain: Res<TerrainGrid>,
    custom_spatial: Res<SpatialGrid<TrackedByDetection>>,
) {
    for (detector_pos, detection) in &detectors {
        // 1. استعلام الجيران من SpatialGrid المخصص (O(1) bucketing بدلاً من O(log n))
        let nearby = custom_spatial.nearby(detector_pos, detection.vision_range);
        
        for (entity, pos, mut stealth) in nearby {
            // 2. فحص خط البصر (Bresenham)
            if !has_line_of_sight(detector_pos, pos, &terrain) { continue; }
            
            // 3. حساب احتمال الكشف
            let distance = detector_pos.distance(*pos);
            let noise_penalty = stealth.noise_level.value();
            let terrain_bonus = terrain.get_stealth_bonus(*pos);
            
            let detection_chance = base_chance * (1.0 - distance/max_range) 
                + noise_penalty - terrain_bonus;
            
            // 4. تحديث DetectionChain
            update_detection_chain(&mut stealth, detection_chance);
        }
    }
}
```

> **ملاحظة**: تم بناء `SpatialGrid` مخصص (انظر القسم 4) بدلاً من `bevy-spatial`. كود Bresenham جاهز للبناء.

## 🟠 4. Spatial Partitioning — ✅ مكتمل (مبني خصيصاً)

### المشكلة في المشروع (كانت)

- `threat_evaluation_system` — O(n²)
- `flanking_calculation_system` — O(n²)
- `stealth_detection_system` — O(n²)

### ✅ ما تم بناؤه

#### SpatialGrid المخصص (`kurulus-core/src/resources/spatial.rs`, `kurulus-systems/src/spatial/mod.rs`)

- **Grid‑based bucketing**: `IVec2` → hash bucket في O(1)
- **نوع معمم**: `SpatialGrid<T: Component>` — يمكن تتبّع أي نوع من المكونات
- **rebuild كل tick**: تكلفة منخفضة لأن buckets يتم تجميعها في `O(n)`
- **علامات مكونات**: `TrackedBySpatial` (للحركة) و`TrackedByDetection` (للرؤية)
- **مدمج في** `SimulationSet::PositionSync`

#### مقارنة مع `bevy-spatial`

|الميزة|SpatialGrid المخصص ✅|`bevy-spatial` KD-Tree|
|---|---|---|
|بنية البيانات|Hash-based bucket|KD-Tree (بالم شجرة)|
|إدراج/حذف|O(1)|O(log n)|
|بحث مدى|O(bucket neighbours)|O(log n + k)|
|إعادة بناء|كل tick (O(n))|عند الطلب (O(n log n))|
|تكامل GridPos|مباشر عبر IVec2|يحتاج تحويل Transform|
|تبعيات|لا شيء|crate خارجي|
|BRP support|مدعوم|غير مدعوم|

> **لماذا اخترنا hash buckets على KD-Tree؟** لأن خرائط Kurulus قائمة على grid (`GridPos(IVec2)`) مع `CELL_SIZE = 1.0`. التحويل من/إلى `Transform` إلى إحداثيات العالم كان سيضيف تعقيداً بدون فائدة. Bucket-based search يعطي O(1) للاستعلام عن الخلايا المجاورة، وهو مثالي لنظام grid.

```
kurulus-systems/src/combat/damage_pipeline.rs
```

#### المكونات:

| المرحلة | الوظيفة | الوصف |
|---------|---------|-------|
| **Stage 1** | `collect_modifiers()` | يجمع كل المعدلات: سلاح، أجهزة، تعزيزات، تشكيل، معنويات، تموضع جانبي ← `DamageContext` |

## 🟡 6. Event System Optimization

### المشكلة في المشروع

- 60+ event types مسجلة في `register_common_events`
- بعض الأنظمة تكتب لنفس الـ events → تكرار

### الحلول المكتشفة

#### Bevy Event Lifecycle:

- Events تبقى لمدة ** frameين** ثم تُحذف تلقائياً
- `EventReader<T>` يخزّن counter للـ last-read event
- Events مخزنة في `Vec<T>` — سريعة لكن تتراكم

#### Observer Pattern (Bevy 0.17+):

```
// بدلاً من EventReader في كل frame
app.add_observer(on_damage_received
    .run_if(|paused: Res<GamePaused>| !paused.0)
    .run_if(resource_exists::<Player>));
```

#### Message System (Bevy 0.17+):

```
// Messages أفضل للـ inter-system communication
fn my_system(mut writer: MessageWriter<DamageEvent>) {
    writer.write(DamageEvent { amount: 10.0 });
}
```

### التوصية لـ Kurulus

```
1. الاحتفاظ بالأحداث الرئيسية (DamageDealt, UnitDied, etc.)
2. دمج الأحداث المتشابهة (إزالة MoveOrder/AttackOrder المكررة)
3. استخدام Observers للأحداث التي تحتاج معالجة فورية
4. استخدام Messages للـ inter-system communication
```

## 🟡 9. Save/Load System

### الحل: `bevy_save` ⭐

- **الإصدار**: 0.18.1 (Bevy 0.16.1)
- **المميزات**:
    - `Snapshot` — serializable snapshot of all saveable resources/entities/components
    - Auto save file management (Windows/Linux/Mac paths)
    - Backend abstraction (FileIO, MockIO)
    - Rollback support

### نمط التكامل:

```
use bevy_save::prelude::*;

// Setup
app.add_plugins(SavePlugin::default());

// Save
fn save_game(world: &mut World) {
    let snapshot = Snapshot::build(world)
        .extract_entities::<With<Saveable>>() // فقط الكيانات القابلة للحفظ
        .extract_resources::<SaveableResources>()
        .build();
    
    snapshot.save(world, "save_01").unwrap();
}

// Load
fn load_game(world: &mut World) {
    Snapshot::load(world, "save_01").unwrap();
}
```

### ملاحظات مهمة من البحث:

- **لا تحفظ Entity IDs مباشرة** — استخدم Strong IDs (مثل `QuestId(u32)`)
- **لا تحفظ runtime-only data** — Systems, Schedules, Event buffers
- **استخدم Bevy Reflect** لتسجيل Types للـ serialization

## 🔵 10. Plugin Architecture & Multi-threading

### نمط Bevy Plugin Ordering (الوضع الحالي):

```
// kurulus-systems/src/lib.rs — الوضع الحالي ✅
pub fn register_logic_plugins(app: &mut App) {
    // Group 1: Core systems
    app.add_plugins((CoreLoopPlugin, WorldMapPlugin, SpatialPlugin, 
                     FlowFieldPlugin, AIPlugin));
    // Group 2: تعتمد على Core
    app.add_plugins((EconomyPlugin, UnitCommandPlugin, CombatPlugin));
    // Group 3: تعتمد على Systems سابقة
    app.add_plugins((StealthPlugin, HeroPlugin, BaseBuildingPlugin));
    // Group 4: Advanced systems
    app.add_plugins((SiegeWarfarePlugin, NavalWarfarePlugin));
}
```

### System Sets Order (الوضع الحالي):

```
SimulationSet::InputProcessing → CommandQueueing → 
AIDecision → AICommandIssuing → 
Pathfinding (← FlowField هنا) → FormationMovement → 
FreeFormMovement (← FlowField movement هنا) → GridQuantization → 
VisionCalculation → StealthDetection → AmbushTrigger → 
ChargeUpdate → FlankingCalculation → ... → ComponentCleanup (← FlowField cleanup هنا) → PositionSync
```

> تم دمج `SpatialPlugin` و `FlowFieldPlugin` في Group 1 للتوفر المبكر للبيانات للأنظمة الأخرى.
