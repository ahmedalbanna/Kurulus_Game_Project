# 📋 التقرير النهائي — بحث عميق في مواضيع Bevy المعقدة لمشروع Kurulus

## ملخص البحث

تم بحث **10 مواضيع حرجة** عبر **+40 مصدر** وتم تحديد **15+ crate** متوافقة مع Bevy 0.15+ وتم تحليل أنماط ECS المطلوبة لكل نظام.

## 🔴 1. Pathfinding في Bevy ECS

### المشكلة في المشروع

- لا يوجد أي pathfinding مُ реализ في الكود حالياً
- GDD يحدد 100+ وحدة في المعركة
- `SimulationSet::Pathfinding` موجود كـ system set لكن بلا أنظمة

### الحلول المكتشفة

#### الخيار A: `bevy_pathfinder` (KBVE) — Flow Field ⭐ الأفضل للـ RTS

- **الإصدار**: 0.1.1 (مايو 2026)
- **الفكرة**: حساب `FlowField` بالـ BFS مرة واحدة لكل هدف، ثم كل وحدة تقرأ الاتجاه تحتها في O(1)
- **المميزات**: Grid-based، chokepoint detection (`FlowGate`)، متوافق مع Bevy 0.18+
- **التكامل مع Kurulus**:
    - `BlockGrid` يمثل `TerrainGrid` الحالي
    - `FlowField::compute(&grid, &[goal])` يُحسب لكل goal مشترك
    - `FlowGate` مفيد لنظام الكمين (ambush detection في الممرات الضيقة)

#### الخيار B: `bevy_northstar` — Hierarchical A* (HPA*)

- **الإصدار**: أحدث إصدار يدعم Bevy 0.15 (v0.7)
- **الفكرة**: تقسيم الخريطة لـ chunks → حساب عقد اتصال بين الـ chunks → A* على المستوى العالي → refinement
- **المميزات**:
    - 5 خوارزميات: `refined()` (HPA*), `coarse()`, `waypoints()`, `astar()`, `thetastar()`
    - دعم 2D/2.5D/3D
    - `Navigation Masks` — تكلفة مختلفة لكل نوع وحدة
    - `Parallel Building` — حساب الـ chunks بالتوازي
    - `Dynamic Changes` — إعادة حساب جزئية عند تغيير الخريطة
- **الأفضل لـ Kurulus**: لأن لكل وحدة هدف مختلف (AI له أهداف متعددة)

#### الخيار C: `bevy_pathfinding` (the-devblog) — Flow Field + Boids

- **الفكرة**: Flow Field + بيدات لتجنب التصادم
- **المميزات**: Spatial partitioning مدمج (bucket system)
- **ملاحظة**: إصدار غير مستقر (0.1.0)

### التوصية لـ Kurulus

```
الخيار B (bevy_northstar) للوحدات التي لها أهداف فردية (AI، أبطال)
+ خيار A (Flow Field) للوحدات التي تهاجم نفس الهدف (تجمعات)
```

### مخطط ECS المقترح

```
// kurulus-core/src/components/pathfinding.rs
#[derive(Component)]
pub struct PathTarget {
    pub target: GridPos,
    pub path: Vec<GridPos>,
    pub current_index: usize,
}

#[derive(Component)]
pub struct Pathfollowing {
    pub speed: f32,
    pub arrival_threshold: f32,
}

// kurulus-core/src/resources/
#[derive(Resource)]
pub struct PathfindingGrid {
    pub blocked: HashSet<GridPos>,
    pub costs: HashMap<GridPos, f32>,
    pub flow_fields: HashMap<GridPos, FlowField>, // cached per goal
}
```

## 🔴 2. AI Behavior Trees في Bevy

### المشكلة في المشروع

- `BehaviorTree` component موجود في `kurulus-core/src/components/ai.rs`
- `AIController` مع strategy/goals
- لكن لا يوجد BT evaluation engine — الكود الحالي يكتب أوامر مباشرة عبر events

### الحلول المكتشفة

#### الخيار A: `big-brain` (Codeberg) — Utility AI ⭐

- **الإصدار**: 0.22+ (يتوافق مع Bevy 0.16، يحتاج fork/تحديث لـ 0.15)
- **الفكرة**: Scorers يقيّمون العالم → Thinkers يختارون أفضل Action بناءً على الـ Score
- **المميزات**:
    - Highly concurrent/parallelizable evaluation
    - Action cancellation مدمج
    - State machine-style continuous actions
    - Reflect support (للـ BRP/MCP)
- **التكامل مع Kurulus**:
    - `Scorer` لكل: health, distance_to_enemy, resources, morale
    - `Action` لكل: MoveTo, Attack, Build, Retreat, Patrol
    - `Thinker` يربط كل AI entity بالـ scorers والـ actions

#### الخيار B: `bevior_tree` — Behavior Tree كـ Bevy Plugin

- **الإصدار**: 0.7 (Bevy 0.15)
- **الفكرة**: BT nodes كـ Bevy components، evaluation عبر systems
- **المميزات**:
    - Sequential, Selector, Parallel nodes
    - بسيط ومباشر
    - لا يحتاج external crate كبيرة

#### الخيار C: `bevy_gearbox` — State Machine-driven AI

- **الفكرة**: States و Transitions كـ entities
- **ملاحظة**: مفيد لـ AI بسيط لكن معقد لـ BT كاملة

### التوصية لـ Kurulus

```
الخيار A (big-brain) للـ AI المعقد (عدو رئيسي)
+ خيار B (bevior_tree) للـ AI البسيط (عمال، مدنيين)
+ الحفاظ على BehaviorTree component الحالي كـ data layer
```

### مخطط ECS المقترح

```
// استخدام big-brain pattern
#[derive(Component, ScorerBuilder)]
pub struct ThreatLevel;

#[derive(Component, ActionBuilder)]
pub struct AttackEnemy;

#[derive(Component, ActionBuilder)]
pub struct RetreatToBase;

// Thinker يربط كلчто معاً
fn setup_ai(entity: Entity, commands: &mut Commands) {
    commands.entity(entity).insert(
        Thinker::build()
            .when(ThreatLevel, AttackEnemy)
            .when(LowHealth, RetreatToBase)
            .otherwise(Patrol)
    );
}
```

## 🔴 3. Stealth/Line-of-Sight في Bevy

### المشكلة في المشروع

- `Stealth`, `DetectionChain`, `VisionCone`, `AmbushState` مُعرّفة
- لا يوجد raycasting أو vision check أو fog of war

### الحلول المكتشفة

#### للـ Line-of-Sight:

**Bresenham's Line Algorithm** — الأبسط والأسرع للـ grid-based:

```
fn has_line_of_sight(from: GridPos, to: GridPos, terrain: &TerrainGrid) -> bool {
    // Bresenham's line algorithm
    // يتحقق من كل cell على الخط بين from و to
    // يُرجع false إذا لقي blocked cell
}
```

#### للـ Fog of War: `bevy_fog_of_war` ⭐

- **المطور**: foxzool
- **الفكرة**: GPU-based fog باستخدام compute shaders
- **المميزات**:
    - `VisionSource` component (circle, square, cone shapes)
    - Chunk-based map processing — مناسب للخريطة الكبيرة
    - Explored area tracking
    - Snapshot system (للـ save/load)
    - `Capturable` entities — تظهر فقط عندما يمر بها vision
- **التكامل مع Kurulus**:
    - كل وحدة لها `VisionSource::cone(vision_range, facing_angle)`
    - `Capturable` على وحدات العدو
    - `FogMapSettings.chunk_size` يتناسب مع `CELL_SIZE = 1.0`

#### للـ Detection System:

```
// detection_system.ts pattern
fn stealth_detection_system(
    mut stealth_query: Query<(Entity, &WorldPosition, &mut Stealth)>,
    detectors: Query<(&WorldPosition, &Detection)>,
    terrain: Res<TerrainGrid>,
    spatial_tree: Res<KDTree3<TrackedByDetection>>, // من bevy-spatial
) {
    for (detector_pos, detection) in &detectors {
        // 1. استعلام الجيران من KD-Tree (O(log n) بدلاً من O(n²))
        let nearby = spatial_tree.within_range(detector_pos, detection.vision_range);
        
        for (entity, pos, mut stealth) in nearby {
            // 2. فحص خط البصر (Bresenham)
            if !has_line_of_sight(detector_pos, pos, &terrain) { continue; }
            
            // 3. حساب احتمال الكشف
            let distance = detector_pos.distance(*pos);
            let noise_penalty = stealth.noise_level.value();
            let terrain_bonus = terrain.get_stealth_bonus(*pos);
            
            let detection_chance = base_chance * (1.0 - distance/max_range) 
                + noise_penalty - terrain_bonus;
            
            // 4. تحديث DetectionChain
            update_detection_chain(&mut stealth, detection_chance);
        }
    }
}
```

/// Stage 1: جمع المعدلات (modifiers)
fn collect_modifiers_system(
    attackers: Query<(&Stats, &Equipment, &ActiveBuffs, &FormationBonus)>,
    targets: Query<(&Health, &CurrentMoraleState)>,

/// Stage 2: حساب الضرر الأساسي
fn calculate_base_damage(ctx: &DamageContext, config: &CombatConfig) -> f32 {
    let effectiveness = config.effectiveness_table.get(ctx.damage_type, ctx.archetype);
    let armor_reduction = config.armor_table.get(ctx.damage_type, ctx.armor_type);
    
    (ctx.attack_damage * effectiveness - armor_reduction).max(0.0)
}

/// Stage 3: تطبيق المعدلات (flanking, crit, morale)
fn apply_modifiers(base_damage: f32, ctx: &DamageContext) -> f32 {

    damage *= ctx.crit_multiplier;
    damage *= ctx.morale_modifier;
    damage *= ctx.formation_modifier;
    damage
}

## 🟡 6. Event System Optimization

### المشكلة في المشروع

- 60+ event types مسجلة في `register_common_events`
- بعض الأنظمة تكتب لنفس الـ events → تكرار

### الحلول المكتشفة

#### Bevy Event Lifecycle:

- Events تبقى لمدة ** frameين** ثم تُحذف تلقائياً
- `EventReader<T>` يخزّن counter للـ last-read event
- Events مخزنة في `Vec<T>` — سريعة لكن تتراكم

#### Observer Pattern (Bevy 0.17+):

```
// بدلاً من EventReader في كل frame
app.add_observer(on_damage_received
    .run_if(|paused: Res<GamePaused>| !paused.0)
    .run_if(resource_exists::<Player>));
```

#### Message System (Bevy 0.17+):

```
// Messages أفضل للـ inter-system communication
fn my_system(mut writer: MessageWriter<DamageEvent>) {
    writer.write(DamageEvent { amount: 10.0 });
}
```

### التوصية لـ Kurulus

```
1. الاحتفاظ بالأحداث الرئيسية (DamageDealt, UnitDied, etc.)
2. دمج الأحداث المتشابهة (移除 MoveOrder/AttackOrder المكررة)
3. استخدام Observers للأحداث التي تحتاج معالجة فورية
4. استخدام Messages للـ inter-system communication
```

## 🟡 9. Save/Load System

### الحل: `bevy_save` ⭐

- **الإصدار**: 0.18.1 (Bevy 0.16.1)
- **المميزات**:
    - `Snapshot` — serializable snapshot of all saveable resources/entities/components
    - Auto save file management (Windows/Linux/Mac paths)
    - Backend abstraction (FileIO, MockIO)
    - Rollback support

### نمط التكامل:

```
use bevy_save::prelude::*;

// Setup
app.add_plugins(SavePlugin::default());

// Save
fn save_game(world: &mut World) {
    let snapshot = Snapshot::build(world)
        .extract_entities::<With<Saveable>>() // فقط الكيانات القابلة للحفظ
        .extract_resources::<SaveableResources>()
        .build();
    
    snapshot.save(world, "save_01").unwrap();
}

// Load
fn load_game(world: &mut World) {
    Snapshot::load(world, "save_01").unwrap();
}
```

### ملاحظات مهمة من البحث:

- **لا تحفظ Entity IDs مباشرة** — استخدم Strong IDs (مثل `QuestId(u32)`)
- **لا تحفظ runtime-only data** — Systems, Schedules, Event buffers
- **استخدم Bevy Reflect** لتسجيل Types للـ serialization

## 🔵 10. Plugin Architecture & Multi-threading

### نمط Bevy Plugin Ordering:

```
// kurulus-systems/src/lib.rs
pub fn register_logic_plugins(app: &mut App) {
    // 1. Core systems أولاً
    app.add_plugins((CoreLoopPlugin, WorldMapPlugin, AIPlugin));
    
    // 2. Systems تعتمد على Core
    app.add_plugins((EconomyPlugin, UnitCommandPlugin, CombatPlugin));
    
    // 3. Systems تعتمد على Systems سابقة
    app.add_plugins((StealthPlugin, HeroPlugin, BaseBuildingPlugin));
    
    // 4. Advanced systems
    app.add_plugins((SiegeWarfarePlugin, NavalWarfarePlugin));
}
```

### System Sets Order:

```
// من system_sets.rs — ترتيب محدد
SimulationSet::InputProcessing → CommandQueueing → 
AIDecision → AICommandIssuing → 
Pathfinding → FormationMovement → FreeFormMovement → GridQuantization → 
VisionCalculation → StealthDetection → AmbushTrigger → 
ChargeUpdate → FlankingCalculation → ... → ComponentCleanup → PositionSync
```

### Multi-threading Concerns:

1. **Bevy auto-batching**: Systems التي لا تتداخل في read/write تُنفّذ بالتوازي
2. **Exclusivity**: `ExclusiveSystem` للأنظمة التي تحتاج world access كامل
3. **Resource locking**: `Res<T>` للقراءة، `ResMut<T>` للكتابة — لا تستخدم Mutex يدوياً
