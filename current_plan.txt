# Hero System — Architecture & Feature Breakdown Plan

  

## Executive Summary

  

The Hero System has a **solid foundation** (core `Hero` component, ability dispatch, XP/leveling, buff tick, hero switching with 10 tests) but has **significant gaps** between the current implementation and the GDD/feature specs. The plan below is organized into 5 phases: first fixing the foundation to match the design docs, then building outward to the advanced subsystems.

## 3. Systems Architecture

  

### 3.1 System Set Ordering

  

The hero systems should run within the existing `SimulationSet` ordering:

  

```

InputProcessing → AbilityActivation → Movement → Combat → BuffApplication →

ComponentCleanup

```

  

**Hero systems mapped to sets:**

  

| System | Set | Notes |

|--------|-----|-------|

| `hero_resource_regen_system` | `SimulationSet::InputProcessing` | Regen resources each tick |

| `hero_ability_system` | `SimulationSet::AbilityActivation` (new) | Validate & dispatch abilities |

| `hero_state_machine_system` | `SimulationSet::Movement` | Transition hero states |

| `hero_knockout_system` | `SimulationSet::Combat` | Handle KO → death blow → recovery |

| `buff_tick_system` | `SimulationSet::BuffApplication` | Tick durations, apply/remove stats |

| `hero_xp_system` | `SimulationSet::HarvestProcessing` | Award XP from kills/objectives |

| `hero_level_up_system` | `SimulationSet::ComponentCleanup` | Check XP, grant levels |

| `equipment_stat_system` | `SimulationSet::BuffApplication` | Apply equipment stat bonuses |

| `hero_death_penalty_system` | `SimulationSet::ComponentCleanup` | Track death penalties |

**Buff stat inflation** (1.7): Currently `buff_tick_system` does:


This adds `damage_bonus` every tick. Fix: store original stats on buff application, restore on removal, or use a separate `EffectiveStats` computed resource.

## 6. Threading & Lifetime Risks

  

| Risk | Mitigation |

|------|------------|

| `buff_tick_system` mutates both `ActiveBuffs` and `Stats` in same query — B0001 conflict with other systems that read Stats | Split into two systems: one to tick durations (read Stats, write ActiveBuffs), one to apply stat modifiers (write Stats via a `StatModifier` resource) |

| `hero_ability_system` takes 13 parameters — potential B0003/B0005 conflicts | Already using two-phase approach (collect activations, then execute). Continue this pattern. Consider `SystemParam` derive for grouping. |

| `equipment_stat_system` writing to `Stats` while `buff_tick_system` also writes to `Stats` | Use an `EffectiveStats` computed resource updated once per frame, or order systems strictly via system sets |

| `Hero.active_cooldowns: HashMap<AbilityId, f32>` — HashMap iteration during mutation | Use `iter_mut()` pattern which is safe in Bevy ECS |

| Co-rule systems need to access two hero entities simultaneously | Use `Query::get()` with explicit entity IDs from `CoCommand` component, not parallel iteration |

| Named unit permadeath persists across missions — needs save/load support | Store in `CampaignState` resource, serialize with `serde` |

## 8. Key Design Decisions to Confirm

  

Before implementation, these should be resolved:

  

1. **HeroId alignment**: Should we keep the extra hero IDs (Orhan, Alaeddin, etc.) in the enum for forward compatibility, or strip them to just Osman/Turgut/Buran and add later? *Recommendation: Keep them — they're harmless and prevent future enum migration.*

  

2. **Buff baseline tracking**: Two approaches:

   - **(A) Store baseline stats on entity** — Add `BaseStats` component, `Stats` is always derived. Clean but requires recalculation.

   - **(B) StatModifier resource** — Centralized stat modification queue processed once per frame. More Bevy-idiomatic but more complex.

   *Recommendation: (A) — simpler, less cross-system coupling.*

  

3. **Equipment RON config format**: Should equipment be defined in per-hero RON files or a global equipment catalog?

   *Recommendation: Global catalog (`equipment.ron`) + per-hero loadout reference.*

  

4. **Named units: separate plugin or inside HeroPlugin?**

   *Recommendation: Inside HeroPlugin — they share stat/combat infrastructure and are not complex enough to warrant a separate crate.*

  

5. **Talent choice UX**: How does the player select talents? Full-screen UI? Quick-select popup?

   *Recommendation: Quick-select popup on level-up (2-3 options), pausing the game briefly. Implement as event-driven UI trigger.*
