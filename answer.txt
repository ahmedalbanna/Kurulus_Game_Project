Here is a technical assessment and architecture feedback for your recommendations regarding the open questions in **Section 12**:

### 1. Selection Events from Render Layer

* **Verdict:** **Strong Agree.** * **Architectural Impact:** Placing `SelectEvent` or `InteractionEvent` variants in `kurulus-core` is the clean, idiomatic way to handle decoupling. Render crates are cross-platform wrappers meant only to convert raw window OS pointer/touch events into meaningful domain abstractions. By pushing raw screen raycasts down to render crates and emitting a shared core event, your simulation state logic inside `kurulus-systems` stays entirely decoupled from your engine internals (e.g., whether you use Bevy or a custom backend).

### 2. FormationType `Skirmish` vs `Scatter`

* **Verdict:** **Agree.** * **Architectural Impact:** Consistency with the Design Document (GDD) specification (`مبعثر`) takes precedence. Keeping dead structural aliases like `Skirmish` can introduce code ambiguity for future developers reading the matching logic or configuring data files. Running a quick automated refactor across the 5+ affected test suites prevents technical debt from mounting during early implementation stages.

### 3. Patrol Route Mechanics

* **Verdict:** **Agree with an Architectural Caveat.** * **Architectural Impact:** Starting with a 2-point ping-pong mechanic handles Phase B scope brilliantly without over-engineering the movement state machines. However, instead of rewriting the structure later, define your component array structure right now to support multiple elements:

```rust
pub struct PatrolRoute {
    pub waypoints: Vec<Vec3>, // Will only contain 2 elements for now
    pub current_index: usize,
}

```

This costs nothing to implement initially, ensures your systems read index-based navigation hooks immediately, and seamlessly scales to multi-waypoint logic later without modifying data schemas.

### 4. Formation Facing Direction

* **Verdict:** **Agree.**
* **Architectural Impact:** Having units automatically rotate to orient their forward vector along their active navigation trajectory prevents clunky visual micro-management on mobile layouts. Overriding with a deliberate rotation function (`Tab + Drag` or touch rotation wheel) can be hooked up directly to your `MoveCommand` event payload once the tactile UI requirements are tackled in later development sprint milestones.

### 5. Garrison Postponement

* **Verdict:** **Strong Agree.**
* **Architectural Impact:** Deferring garrison systems minimizes scope creep. Core movement systems, pathfinding constraints, and basic combat loops are critical paths. Postponing target collection wrappers and spatial nesting logic (putting units inside structures) preserves developer velocity for more important tasks.
